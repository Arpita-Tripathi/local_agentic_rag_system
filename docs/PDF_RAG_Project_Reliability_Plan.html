Decision: does this pipeline need an API?

No API is required for PDF extraction, OCR, embeddings, retrieval, citations, or the notebook’s current local LiteRT/Gemma path. The notebook sets LiteRT as the default provider and also contains an OpenRouter cloud option. Keep local as the default; add a cloud API only if a measured evaluation shows the local model cannot meet answer quality, speed, or hardware needs.

Local-only modePrivate documents; no per-question provider API call. Needs model downloads and suitable CPU/GPU.
Optional cloud modeOne answer call with retrieved excerpts, for public/non-sensitive documents and a configured key/quota.
Never requiredDo not send every page, every chunk, or every image to an API by default.

01 · Choose operating mode

Which mode should we build first?

Pick a use case to see the practical trade-off. This only changes the explanation; it does not call any model.

Recommended first release: local-first with optional cloud switch

Start by preserving the notebook’s local LiteRT setup and making it reliable. Add one provider adapter for Gemini only after the benchmark. Keep provider choice on the server/in environment config—never expose an API key in HTML or browser code.

02 · Target architecture

What happens, and where

Index-time work happens once per document. Question-time work should stay small, bounded, and source-aware.

1Validate uploadPDF type, size/page bounds, encryption and safe temporary-file handling.LOCAL · INGEST
2Extract pagesSimple text path first. Detect empty/image-only pages before deciding OCR.LOCAL · INGEST
3OCR / layout fallbackTesseract or Docling only for scanned, table-heavy or layout-sensitive pages.LOCAL · CONDITIONAL
4Chunk with provenanceStore stable chunk ID, page, heading, content type and parser version.LOCAL · INGEST
5Build/reuse indexDense embeddings + BM25; persist index and invalidate it when source/settings change.LOCAL · ONCE
6Retrieve + rankHybrid retrieval, optional local reranker after evaluation; select a small evidence set.LOCAL · PER QUESTION
7Answer from evidenceLocal model by default; optional cloud API gets excerpts only, not the entire PDF.LOCAL OR OPT-IN API
8Validate & show sourcesValidate returned chunk IDs locally; map them to clickable PDF page citations.LOCAL · PER QUESTION

04 · Open-source shortlist

Useful tools—not all at once

Start with the smallest stack that passes the evaluation. Open-source code does not automatically mean every model weight, dependency, or hosted API is under the same license.

Docling

MIT · repo

Advanced PDF layout, reading order, tables, OCR, Markdown/JSON export and local/air-gapped execution. Good complex-PDF fallback; benchmark its install/runtime on target hardware.

Repository & docs ↗

pypdf

Check repo license

Small, pure-Python option for basic PDF text and metadata extraction. A good lightweight baseline; it is not an OCR engine and will not solve complex visual layouts alone.

Repository ↗

Tesseract OCR

Apache-2.0 · repo

Local OCR with UTF-8 and 100+ language data packages. OCR only pages that need it; select and test the right language packs, including Hindi/English if needed.

Repository ↗

Current MiniLM + BM25

Keep baseline

Existing local hybrid retrieval is already a useful baseline. Preserve a measured baseline before swapping models or adding a vector database.

Model card ↗

Multilingual MiniLM

Apache-2.0 · model card

`paraphrase-multilingual-MiniLM-L12-v2` lists Hindi among supported languages. Candidate for mixed Hindi/English queries; evaluate against current model before switching.

Model card ↗

BGE-M3 / FlagEmbedding

MIT · code/model card

Multilingual dense + sparse retrieval; the project recommends hybrid search and optional reranking. More capable, but heavier than the simplest baseline—make it a benchmark candidate, not an automatic dependency.

Model card ↗ · Toolkit ↗

Ragas

Apache-2.0 · repo

RAG evaluation and test-set tooling. Use after creating a trusted golden set; LLM-judge metrics may require a model/API, so start with deterministic retrieval/citation tests.

Repository ↗

Qdrant

Apache-2.0 · repo

Vector database for many PDFs, persistent collections, filters and larger-scale deployments. Not necessary for a single small PDF: current NumPy/BM25 can be simpler.

Repository ↗

Ollama

Runtime ≠ model license

Local model runner with an HTTP API, useful as an alternative to LiteRT for a demo or developer machine. Each model has its own license and hardware requirements.

Repository ↗

Streamlit / FastAPI

Optional UI / API

Streamlit is a quick Python UI for upload, chat and citations. FastAPI is useful if the frontend and backend need a clean service boundary. Pick one UI path for MVP.

Streamlit ↗ · FastAPI ↗

05 · Implementation roadmap

Proceed in this order

Build a small, testable product first. Do not add a vector database, agent framework or extra provider until the evidence says you need it.

Phase 0 · Baseline

Make the current notebook reproducible

Record current behavior before refactoring.

  • Split notebook logic into ingest, retrieval, provider, answer and UI functions/modules.
  • Lock dependencies; remove unused/duplicate packages after checking imports.
  • Keep LiteRT default; make environment setup and model download explicit, with actionable errors.
Gate: clean restart works
Phase 1 · MVP

Reliable local text-PDF Q&A

Ship one solid path before handling every PDF edge case.

  • Page-aware text extraction, chunk IDs, local hybrid search and one answer call.
  • Validate cited chunk IDs and map them to page numbers.
  • Add honest “not found” response; cap optional retry to one.
Gate: citations verified
Phase 2 · Robust docs

Handle scanned PDFs, tables and figures

Add complexity only where input tests expose a gap.

  • Detect image-only pages; run local Tesseract OCR only on those pages.
  • Try Docling for layout/table-heavy PDFs; keep parser choice observable.
  • Move image/table summaries to on-demand or explicit batch enrichment instead of mandatory whole-document inference.
Gate: mixed PDF test set
Phase 3 · Quality

Prove retrieval and answer quality

Build an evaluation set before optimizing prompts or models.

  • Create at least 50–100 human-checked questions across answerable, unanswerable, Hindi/English, table and OCR cases.
  • Compare current English MiniLM to multilingual MiniLM; optionally benchmark BGE-M3 and local reranker.
  • Report retrieval Recall@k, citation accuracy, answer support, abstention and latency.
Gate: target metrics pass
Phase 4 · Demo

Make the project memorable and safe

Show evidence and product choices, not just a chatbot bubble.

  • Build a clean Streamlit UI: upload progress, page preview, clickable citations and evidence snippets.
  • Offer “local only” and “send excerpts to cloud” modes with explicit consent.
  • Add document delete/clear, key setup via environment secrets, usage indicator, and visible model/parser provenance.
Gate: demo from fresh setup
06 · Reliability & standout bar

Define what “good” means

Targets below are proposed project acceptance goals—not published benchmark results. Adjust them after a baseline run on the chosen PDFs and hardware.

Retrieval quality≥ 90%Recall@5 on questions with gold evidence.
Page citation accuracy≥ 95%Shown page really contains cited support.
Unsupported claims0 targetOn the curated answerable/unanswerable test set; report misses honestly.
Question-time cloud calls≤ 1Normal case; one bounded retry only if enabled.

For evaluation, keep a fixed, versioned set of source PDFs, questions, expected evidence pages and answerability. Measure end-to-end latency on the actual laptop/Colab runtime. Do not claim a percentage improvement or “hallucination-free” without measured results.

08 · API and data terms

Free does not mean unlimited or private

Recommended cloud policy Gemini Flash-Lite is a candidate, not a hard dependency: confirm the exact model and your project’s current free eligibility, RPM/TPM/RPD limits, region and terms in AI Studio before integrating. Google’s unpaid-service terms say submitted inputs/outputs may be used to improve services and may be processed by human reviewers; do not send confidential, personal or sensitive PDFs on the unpaid tier. Keep cloud use opt-in and send only retrieved excerpts. OpenRouter `:free` variants have a platform cap (currently documented as 20 requests/minute and 50/day for accounts with under $10 lifetime credits), with upstream model limits also possible.
